# パフォーマンスのプロファイル

[English](requirements.md)

## この文書について

パフォーマンスのプロファイルは、kuromojin の 1 つのビルドを、決まったテキストのセットで計測します。計測するのは、辞書を読み込む時間、解析の時間、メモリ、アロケーション、インストールされるサイズ、CPU 時間がどこで使われるかです。
比較は、2 つのビルドのプロファイルを交互に取ります。2 つのビルドは、ベース（`master` など）とヘッド（プルリクエスト）です。比較は、2 つのプロファイルをその比と並べて表示し、トークンが異なるテキストも表示します。
変更の作者、AI エージェント、レビューする人は、変更をマージする前に、その変更がパフォーマンスに何をするかを見られます。だれも気づかないまま kuromojin が遅くなったり大きくなったりしないようにするためです。
開発者と AI エージェントは、プロファイルと比較を手元で実行します。CI は、プルリクエストごとに比較を実行し、その出力をジョブのサマリーに入れます。
親の Product は [kuromojin](../../product.ja.md) です。この機能は、日本語のルールを実行する書き手のために、Product の価値「実行の小さな一部で済む解析」を保ちます。この機能を使うのは、kuromojin を変更する人と AI エージェントです。

### 範囲

- 1 つのビルドのプロファイル：何を計測するか、テキストのセット、Markdown と JSON と CPU プロファイルとしての出力
- 2 つのビルドの比較
- プルリクエストに対して比較を実行する CI のジョブ。フォークからのプルリクエストを含む
- 比較を実行してその出力をプルリクエストに入れるという、AI エージェントへの指示

### 範囲外

- 変更を受け入れられるかどうかを決めること。比較は違いを示し、人が決める
- 違いを理由に CI を失敗させること。CI は結果を示し、違いでは失敗しない
- プルリクエストへのコメント
- kuromojin の呼び出し側が、自分の実行について取るプロファイル。パッケージは、プロファイルのための API を持たない。プロファイルは、すべての呼び出し側が使う関数を通して、ビルドを外から計測する
- `master` のプロファイルの履歴
- textlint の実行の時間。実行するルールは、それぞれのリポジトリに属する

## ユーザーストーリー

### プルリクエストを開く前に、変更が何をするかを見る

解析器、辞書の読み込み、辞書、トークンの再利用を変更する開発者または AI エージェントとして、自分のブランチを `master` と比較する 1 つのコマンドがほしい。違いをプルリクエストの説明に入れられるようにするためだ。

**受け入れ基準：**

シナリオ：ヘッドが解析を速くすると、出力は解析についてそれを示す

- Given: ヘッドは、テキストを速く解析するように解析器を変更している。ベースは `master` である。
- When: 開発者が比較を実行する。
- Then: Markdown の出力は、ベースとヘッドの解析の時間をその比とともに表示し、比に速くなったという印を付ける。それぞれのビルドで CPU 時間がもっとも長い関数も表示する。

シナリオ：ヘッドがテキストのトークンを変えると、出力はそのテキストを一覧にする

- Given: ヘッドは、セットの 1 つの行がほかのトークンになるように解析器を変更している。
- When: 開発者が比較を実行する。
- Then: 出力は、1 つの行でトークンが異なると示し、その行を、それぞれのビルドで最初に異なるトークンとともに表示する。

シナリオ：ヘッドがより多くのメモリを持ち続けると、出力はメモリに印を付ける

- Given: ヘッドは、もっとも長いテキストの作業用のメモリを持ち続けるように解析器を変更している。時間の変化は、そのノイズより小さい。
- When: 開発者が比較を実行する。
- Then: 出力は、解析の後のメモリに大きくなったという印を付け、ベースとヘッドのメモリをその比とともに表示する。

シナリオ：ヘッドがビルドを変えないと、出力は何も変わっていないと示す

- Given: ヘッドは、ドキュメントだけを変更している。
- When: 開発者が比較を実行する。
- Then: 出力は、トークンが同じであると示し、ベースとヘッドの数値を印なしで表示する。

シナリオ：ベースがほかのコードで解析していても、すべての項目を比較する

- Given: ベースは、解析をほかのパッケージが行うコミットである。ヘッドは、自分の解析器を持つ。
- When: 開発者が比較を実行する。
- Then: 出力は、両方のビルドについてすべての項目を持つ。どの項目も、`getTokenizer` と `tokenize` を通して、またはビルドのファイルから計測するからである。

### 1 つのビルドで時間がどこに使われるかを見つける

速くできるところを探す開発者として、作業ツリーだけのプロファイルがほしい。ほかのコミットをビルドせずに、数値と遅い関数を見られるようにするためだ。

**受け入れ基準：**

シナリオ：プロファイルを実行すると、作業ツリーのすべての項目を表示する

- Given: 作業ツリーはビルドされている。
- When: 開発者がプロファイルを実行する。
- Then: Markdown の出力は、選んだセットごとにプロファイルのすべての項目を表示し、CPU 時間がもっとも長い関数を表示する。

シナリオ：プロファイルまたは比較が終わると、CPU プロファイルが残る

- Given: プロファイルまたは比較を実行した。
- When: 開発者が、出力のディレクトリまたは CI のアーティファクトを開く。
- Then: そこには、セットごとに、それぞれのビルドの CPU プロファイルがある。形式は、Chrome DevTools が開けるものである。

### ほかの人のプルリクエストでの変化に気づく

プルリクエストをレビューするメンテナーとして、CI に比較を実行してほしい。プルリクエストを手元でビルドして計測しなくて済むようにするためだ。

**受け入れ基準：**

シナリオ：プルリクエストがソースを変更すると、CI は比較をジョブのサマリーに入れる

- Given: フォークからのプルリクエストが、`src/` より下のファイルを変更している。
- When: そのプルリクエストに対して CI が実行される。
- Then: ジョブのサマリーには、プルリクエストのベースのコミットとヘッドを比較した Markdown の出力がある。実行には、JSON の出力と CPU プロファイルがアーティファクトとしてある。違いがあっても、ジョブは失敗しない。

シナリオ：プルリクエストのコードが悪意のあるものでも、シークレットと書き込みの権限を得られない

- Given: フォークからのプルリクエストが、環境を出力してリポジトリにプッシュするように、プロファイルのスクリプトを変更している。
- When: そのプルリクエストに対して CI が比較を実行する。
- Then: ジョブは、リポジトリのシークレットを持たず、読み取りだけができるトークンを持つ。プッシュは失敗し、実行の外にあるものは何も変わらない。

シナリオ：プルリクエストがドキュメントだけを変更すると、比較は実行されない

- Given: プルリクエストが、`docs/` より下の Markdown ファイルだけを変更している。
- When: そのプルリクエストに対して CI が実行される。
- Then: 比較のワークフローは実行されない。

### AI エージェントから結果を読む

プルリクエストをレビューする、または遅くなった原因を調べる AI エージェントとして、結果を JSON でほしい。表を解析せずに数値を読めるようにするためだ。

**受け入れ基準：**

シナリオ：比較が終わると、JSON は両方のビルドと変わったことを持つ

- Given: 比較を実行した。
- When: エージェントが JSON の出力を読む。
- Then: JSON は、ベースとヘッドのコミット、テキストのセット、両方のビルドのすべての項目とその比と印、トークンが異なるテキスト、それぞれの関数の CPU 時間を持つ。

## KPI

なし。この機能には指標を定めていない。

## 機能要件

### プロファイル

**概要：** kuromojin の 1 つのビルドを、テキストのセットで計測する。

**入力：** テキストのセット。ビルドは作業ツリーである。

**出力：** 標準出力への Markdown と、出力のディレクトリへの Markdown、JSON、CPU プロファイル。

#### 適用条件

##### 計測するもの

どの項目も、ビルドの `getTokenizer` と `tokenize` を通して、またはビルドのファイルから計測する。プロファイルは、パッケージの内側にあるものを読まず、呼び出さない。そのため、内側が異なる 2 つのビルドも同じ方法で計測する。

| 項目 | 方法 | 理由 |
| --- | --- | --- |
| トークン | セットのすべての行とすべてのファイルのトークン | テキストのトークンは、メジャーバージョンでだけ変わる。比較は、トークンが異なるテキストを表示する |
| 辞書の読み込み | 何も読み込んでいないプロセスで、モジュールを読み込み始めてからトークナイザーを得るまでの時間。複数のプロセスで計測する | 書き手は、実行のたびに 1 回これを払う |
| 読み込みの後のメモリ | 読み込みの後に、ガベージコレクションを行ってから、プロセスが使っているメモリ | 辞書は、実行の間ずっとメモリにある |
| 行ごとの解析 | トークンを再利用せずに、セットのすべての行をトークナイザーで解析する時間。解析を繰り返し、もっとも速い回を採用する | ルールは文のトークンを求めるので、これが実行の中での kuromojin の主な仕事である |
| ファイルごとの解析 | セットのそれぞれのファイルを 1 つのテキストとして解析する時間 | 長いテキストは大きな作業用のメモリを必要とし、短い行ではそれが現れない |
| 覚えているテキストの `tokenize` | トークンを覚えているテキストに対する、`tokenize` の 1 回の呼び出しの時間 | 多くのルールを使う実行では、ほとんどの呼び出しがここで終わる |
| 解析のアロケーション | すべての行の解析が割り当てるバイト数と、ガベージコレクションの回数と停止時間 | アロケーションは、呼び出し側の実行でガベージコレクションの停止になる |
| 解析の後のメモリ | すべての行の `tokenize` とすべてのファイルの解析の後に、ガベージコレクションを行ってから、プロセスが使っているメモリ | kuromojin が持ち続けるものを示す。覚えているトークンと、作業用のメモリである |
| インストールされるサイズ | パッケージのファイルのサイズと、依存するパッケージのファイルのサイズ | 書き手は、プロジェクトごとにこれらをインストールする |
| CPU 時間 | 読み込みと解析の CPU プロファイルを、パッケージごと、関数ごとに合計したもの | どの関数を見ればよいかがわかる |

解析が遅いビルドは、少ない繰り返しで計測する。それでも、どの計測も少なくとも 1 回は実行するので、すべての項目が数値を持つ。

##### テキストのセット

| セット | テキスト |
| --- | --- |
| small | このリポジトリの日本語のドキュメント |
| medium | 公開されているリポジトリの日本語のドキュメント。コミットはプロファイルが固定する |

セットは、行とファイルを持つ。行は、ドキュメントの空でない行であり、ルールが渡す文の代わりである。ファイルは、ドキュメントの全体のテキストである。
medium のセットは、最初に使うときにダウンロードし、そのマシンに残す。比較する 2 つのビルドは、いつも同じテキストを受け取る。
セットを選ばないときは、すべてのセットを使う。

##### 出力

Markdown の出力は、セットごとに、ファイルの数、行の数、文字の数と、項目の表を表示する。
セットの後に、インストールされるサイズを表示する。CPU 時間がもっとも長いパッケージと関数も表示する。
出力のディレクトリには、同じ Markdown、すべての数値を持つ JSON、CPU プロファイルを書く。

#### 例外的な動作

##### 作業ツリーがビルドされていない

プロファイルは、最初に作業ツリーをビルドする。開発者がビルドしないように指定し、ビルドがないときは、ビルドの方法を伝えるメッセージを出して止まり、結果を書かない。

##### 知らないセット

プロファイルは、何かを計測する前に、セットの名前を挙げるメッセージを出して止まる。

##### medium のセットをダウンロードできない

プロファイルは、リポジトリとコミットを挙げるメッセージを出して止まり、結果を書かない。small のセットは、ダウンロードを必要としない。

##### 計測が失敗する

ビルドがあるテキストで例外を投げるなどして、ビルドの計測が失敗したとき、プロファイルは、ビルド、セット、計測の名前を挙げ、ビルドのエラーを付けたメッセージを出して止まる。結果は書かない。

### 比較

**概要：** 2 つのビルドのプロファイルを同じセットで取り、違いを表示する。

**入力：** ベース（Git の ref。既定は `master`）と、テキストのセット。ヘッドは作業ツリーである。

**出力：** プロファイルの出力に、両方のビルドの数値、その比、変わったことを加えたもの。

#### 適用条件

##### ビルド

ベースは、作業ツリーの外のディレクトリで、そのコミットからビルドする。ビルドは、同じコミットとの次の比較のために残す。
ベースの依存パッケージは、そのコミットがロックしているものである。
2 つのビルドの計測は、交互に実行する。マシンの負荷の変化が、両方に届くようにするためである。
CPU プロファイルでは、両方のビルドが同じ仕事をする。そのため、2 つのプロファイルの間で、関数の時間を比べられる。

##### 変わったこと

出力は、セットごとの変わったことから始まる。読む人が、何かが変わったかどうかをひと目で見られるようにするためである。
項目の比は、ヘッドの数値をベースの数値で割ったものである。
比が表の範囲の外にある項目に、印を付ける。小さすぎて計測できない違いには、印を付けない。
インストールされるサイズは、合計に印を付け、その 2 つの内訳には付けない。ファイルが、パッケージと依存パッケージの間で移るからである。

| 項目 | 遅い、または大きいという印を付ける比 | 速い、または小さいという印を付ける比 |
| --- | --- | --- |
| 行ごとの解析、ファイルごとの解析、覚えているテキストの `tokenize` | 1.1 倍以上 | 0.91 倍以下 |
| 辞書の読み込み | 1.2 倍以上 | 0.83 倍以下 |
| メモリ、割り当てるバイト数、インストールされるサイズ | 1.1 倍以上 | 0.91 倍以下 |
| ガベージコレクションの停止時間 | 1.3 倍以上 | 0.77 倍以下 |

行またはファイルのトークンが異なるとき、出力は、そのような行とファイルの数を表示する。そのうちの最初の 10 個は、それぞれのビルドで最初に異なるトークンとともに表示する。

#### 例外的な動作

##### ベースが存在しない、またはビルドできない

比較は、その ref、または失敗した手順を挙げるメッセージを出して止まり、何も計測しない。

### CI のジョブ

**概要：** プルリクエストに対して比較を実行する。

**入力：** ソース、辞書、プロファイルのスクリプト、ビルドと依存パッケージを決めるファイル、ワークフローのどれかを変更するプルリクエスト。

**出力：** ジョブのサマリーに入れた Markdown の出力と、アーティファクトにした出力のディレクトリ。

#### 適用条件

ベースはプルリクエストのベースのコミットであり、ヘッドはプルリクエストである。
ジョブは、すべてのセットを使う。
ジョブは、比較を終えられないときだけ失敗する。ビルドの間の違いでは失敗しない。
ジョブはプルリクエストのコードを実行するので、シークレットを持たず、読み取りだけができるトークンを持つ。

### AI エージェントへの指示

**概要：** リポジトリで作業する AI エージェントに、プロファイルと比較をいつ実行するかを伝える。

**入力：** 解析器、辞書の読み込み、辞書、トークンの再利用への変更。

**出力：** プルリクエストの説明に入れた、比較の出力。

#### 適用条件

リポジトリの AI エージェント向けの指示は、2 つのコマンドの名前を挙げ、そのような変更では Markdown の出力をプルリクエストの説明に入れるように伝える。

## データ要件

### 必要なデータ

- **テキストのセット：** ビルドが解析するドキュメント。公開されているドキュメントであり、medium のセットは、ダウンロードの後にマシンに残る
- **ベースのビルド：** ベースのコミットのファイルと、その依存パッケージ。次の比較のためにマシンに残る
- **結果：** それぞれのビルドの数値、トークンの違い、CPU プロファイル。出力のディレクトリのファイルであり、CI では実行のアーティファクトである

### 関係

結果は、1 つまたは 2 つのビルドと、選んだセットに属する。

### 個人情報

なし。セットは公開されているドキュメントであり、結果は人についての情報を持たない。CPU プロファイルは、実行したマシンでの、ビルドのファイルのパスを持つ。

## 外部サービスへの依存

- **GitHub**
  - **関連するユーザーストーリー：** medium のセットについては、すべて。CI のジョブについては、「ほかの人のプルリクエストでの変化に気づく」
  - **依存する理由：** medium のセットは GitHub の公開リポジトリであり、CI のジョブは GitHub Actions で動く
  - **契約と利用についての判断：** ダウンロードにアカウントは必要ない。CI のジョブは、公開リポジトリの無料の実行時間を使う

## セキュリティの考慮事項

CI のジョブは、プルリクエストのコードを実行する。フォークからのものも含む。
ジョブは、リポジトリのシークレットも、書き込めるトークンも持ってはならない。

## 未解決事項

- **印を付ける範囲：** 表の範囲は、最初の選択である。何も変えていないプルリクエストに CI が印を付けたとき、または人が気づく変化を見逃したときに見直す。azu が決める。
